# Database Migrations - Be New Application

This directory contains all Liquibase database migrations for the Be New employee onboarding application.

## Overview

The database schema is built using PostgreSQL 16 with the following design principles:
- **UUID primary keys** generated by Spring Boot application
- **No Row-Level Security (RLS)** - authorization handled in application layer
- **Denormalized progress counters** for fast dashboard queries
- **Template versioning via denormalization** - task copying strategy
- **ON DELETE RESTRICT** for all foreign keys - deletion logic in application

## Schema Structure

```
benew (schema)
├── app_user              [Users: Admin, Manager, Employee]
├── template              [Checklist templates per position]
├── template_task         [Tasks in templates]
├── onboarding_process    [Employee onboarding instances]
└── onboarding_task       [Tasks copied from template]
```

## Database Roles

### app_owner
- **Purpose**: Schema ownership and DDL operations
- **Usage**: Liquibase migrations only
- **Permissions**: Full DDL (CREATE, ALTER, DROP)
- **⚠️ Security**: Never use in application code

### app_spring
- **Purpose**: Application runtime operations
- **Usage**: Spring Boot application
- **Permissions**: DML only (SELECT, INSERT, UPDATE, DELETE)
- **⚠️ Security**: No DDL permissions

## Naming Conventions

### Migration Files
Format: `YYYYMMDDHHmmss_short_description.sql`
- `YYYY` = Year (e.g., 2025)
- `MM` = Month (01-12)
- `DD` = Day (01-31)
- `HH` = Hour (00-23) UTC
- `mm` = Minute (00-59)
- `ss` = Second (00-59)

### Database Objects
- **Tables**: `snake_case` (e.g., `app_user`, `onboarding_process`)
- **Columns**: `snake_case` (e.g., `first_name`, `created_at`)
- **Indexes**: `idx_{table}_{columns}` (e.g., `idx_app_user_email_lower`)
- **Foreign Keys**: `fk_{table}_{ref_table}` (e.g., `fk_app_user_manager`)
- **Unique Constraints**: `uk_{table}_{columns}` (e.g., `uk_app_user_email`)

## Key Design Decisions

### 1. UUID Primary Keys
- Generated by Spring Boot: `@GeneratedValue(strategy = GenerationType.UUID)`
- No database functions (`gen_random_uuid()`) used
- Benefits: Distributed ID generation, no sequence bottlenecks

### 2. No Row-Level Security (RLS)
- Authorization logic in Spring application layer
- Simpler implementation for MVP
- Easier testing and debugging
- Example: Managers see only their employees via `WHERE manager_id = :currentUserId`

### 3. Denormalized Progress Counters
- `onboarding_process` stores `total_tasks_count` and `completed_tasks_count`
- Updated by application when tasks change
- Eliminates expensive `COUNT(*)` queries on dashboard
- Progress % = `(completed_tasks_count / total_tasks_count) * 100`

### 4. Template Versioning via Denormalization
- Tasks are **COPIED** from `template_task` to `onboarding_task` when process starts
- Changes to templates do NOT affect active onboarding processes
- `source_template_id` kept for audit purposes only

### 5. ON DELETE RESTRICT
- All foreign keys use `ON DELETE RESTRICT`
- Application must handle deletion logic:
  - Can't delete manager with assigned employees
  - Can't delete user with active onboarding
  - Can't delete template used in processes

### 6. Case-Insensitive Uniqueness
- Functional indexes: `LOWER(email)`, `LOWER(position_name)`
- Application MUST normalize before insert/search
- Prevents duplicates like "user@example.com" and "User@example.com"

## Running Migrations

### Using Liquibase CLI

```bash
# Update database to latest version
liquibase --changelog-file=liquibase/changelog-master.xml update

# Rollback last migration
liquibase --changelog-file=liquibase/changelog-master.xml rollback-count 1

# Validate migrations
liquibase --changelog-file=liquibase/changelog-master.xml validate

# Generate rollback SQL (preview)
liquibase --changelog-file=liquibase/changelog-master.xml rollback-sql
```

### Using Spring Boot

Add to `application.yml`:

```yaml
spring:
  liquibase:
    enabled: true
    change-log: classpath:liquibase/changelog-master.xml
    default-schema: benew
    liquibase-schema: public
    user: app_owner  # Use owner role for migrations
    password: ${DB_OWNER_PASSWORD}
```

Migrations run automatically on application startup.

## Index Strategy

### Foreign Key Indexes (Migration 4)
- **Purpose**: Optimize JOIN operations
- **Created on**: All UUID foreign key columns
- **Impact**: O(n) → O(log n) for joins
- **Critical for**: Dashboard queries, task loading

### Search Indexes (Migration 5)
- **Purpose**: Optimize filtering and search
- **Includes**: Case-insensitive email/position, name search, status filtering
- **Impact**: O(n) → O(log n) for searches
- **Critical for**: User search, authentication, template lookup

### Composite Indexes (Migration 6)
- **Purpose**: Optimize multi-condition queries
- **Examples**: 
  - `(manager_id, status)` for dashboard
  - `(template_id, task_order)` for ordered task lists
- **Impact**: Single index scan instead of bitmap scan
- **Critical for**: Manager dashboard performance

## Performance Considerations

### Query Optimization Tips

1. **Always use LOWER() for case-insensitive searches**:
   ```sql
   -- ✅ Good (uses index)
   WHERE LOWER(email) = LOWER(:email)
   
   -- ❌ Bad (full table scan)
   WHERE UPPER(email) = UPPER(:email)
   ```

2. **Leverage composite indexes**:
   ```sql
   -- ✅ Good (uses idx_onboarding_process_manager_status)
   WHERE manager_id = ? AND status = 'ACTIVE'
   
   -- ❌ Less optimal (uses only manager_id index)
   WHERE manager_id = ? OR status = 'ACTIVE'
   ```

3. **Use progress counters instead of COUNT()**:
   ```sql
   -- ✅ Good (denormalized counter)
   SELECT completed_tasks_count, total_tasks_count FROM onboarding_process
   
   -- ❌ Bad (expensive COUNT)
   SELECT COUNT(*) FILTER (WHERE is_completed) FROM onboarding_task
   ```

## Troubleshooting

### Common Issues

1. **"relation does not exist" error**
   - Ensure schema search_path includes `benew`
   - Set in connection URL: `?currentSchema=benew`

2. **Slow dashboard queries**
   - Check if indexes were created: `\d benew.onboarding_process`
   - Verify query uses index: `EXPLAIN ANALYZE ...`

3. **Permission denied errors**
   - Verify using correct role (`app_owner` for migrations, `app_spring` for app)
   - Check grants: `\du` and `\dp benew.*`

4. **Unique constraint violations**
   - For email: Check case-insensitive duplicates with `LOWER(email)`
   - For position: Ensure application normalizes before insert

## Rollback Strategy

Each migration includes rollback commands. To undo migrations:

```bash
# Rollback last migration
liquibase rollback-count 1

# Rollback to specific date
liquibase rollback-to-date "2025-11-03"

# Generate rollback SQL (preview without executing)
liquibase rollback-sql
```

⚠️ **WARNING**: Rollbacks are destructive! Always backup data first.
